## 目的

验证一条链路：一次任务的 workspace 被挂起（pause）之后，恢复（resume）的那一轮还能把交付走完、落到这次运行对应的 PR 分支上，而不是丢掉这次运行。观察三件事：

- 恢复之后，交付是否照常推到 PR 分支；
- 恢复的那一轮是否守住了「勿改业务代码」的边界；
- 恢复前后的产物是否留下了可复核的痕迹。

## 这份演练证明了什么、没证明什么

- **证明了**：一次带 `resume` 的运行能把改动推到它的 PR 分支并开成 PR；恢复后的那一轮没有越界去改业务代码，diff 里只有文档。
- **没有证明**：恢复是**从暂停点继续**，而不是**从头再来一遍**。恢复后要做的事与暂停前完全一致——都是写一个标记再交付——这两种情形在结果上不可区分，本次没有留下任何能区分它们的痕迹。
- **没有证明**：workspace 的中间状态被完整保存。本次没有「暂停前后各有实际文件变更」的场景，因此也无从验证写了一半的文件、推了一半的分支在恢复时会不会重复写入或丢失。要验证那一点，需要一次在交付中途暂停、且暂停点前后都有实际文件变更的演练。

一句话：这次证明的是**链路通**，不是**状态被正确保存**。链路通不等于恢复语义正确。

这也是本文件不再只留一行标记的原因：一行「事后补出来」的标记，恰恰是上面那个不可区分问题的例子；把它换成有基准提交、有观测提交、有「没证明什么」清单的记录，reviewer 才能自己复核这份演练做到了哪一步。

## 为什么文件名带运行 ID、为什么放在 `docs/drills/`

这两点不是格式偏好，是这条链路之前暴露出来的约束：

- **文件名带运行 ID**：这类演练会并行跑。暂停演练同一批就有 `#82`（`e2e-pause-mvwk1505`）、`#87`（`e2e-pause-mvwk6zv5`）、`#92`（`e2e-pause-mvwkdp7r`）：三条分支 `9296bf5`、`e2c56ba`、`001f795` 的父提交都是 `21d15d4`，各自向同一个根目录 `pause-demo.md` 添加一行不同内容。产物同名，并行合并时要么冲突（add/add，需要人工解）、要么只能留下一份；只看根目录这个文件名，分不出是第几次运行的。目前这三条分支都还没合进 `main`，所以「证据丢失」还没有真正发生过——这只是可以预见的麻烦，不是已观测到的事故。带上运行 ID，并行几次都能并存。
- **放在 `docs/drills/`**：仓库根目录只留 `README.md`，其余文档都在 `docs/`。这个约定在 `origin/main` 上还复核不到，先例都在未合并分支上：`ac1a616`（PR #73，未合并）把根目录的 `followup-demo.md` 删掉、改成 `docs/followup-demo.md`；`b011e54`（PR #93，未合并）把 `pause-demo.md` 换成 `docs/drills/pause-demo-mvwkdp7r.md`。本文件沿用同一约定，也是 `docs/drills/` 第一次落到 `main` 上。不再往根目录放标记文件。
