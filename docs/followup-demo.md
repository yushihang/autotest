# 跟进交付演示（followup delivery demo）

这份演示用来验证「PR 被打回 review 意见后，follow-up 交付还能照常把改动落到 PR 分支上」这条链路：review 给了 COMMENT，平台起一次新的跟进运行，它在本分支上改完文件、由平台提交并推送，而不是由 agent 自己 commit/push。

| 项 | 值 |
|---|---|
| 所属 | issue #72 的跟进交付演示（PR #73） |
| 运行 ID | `e2e-followup-mvwipxnm` |
| 改动范围 | 只碰文档：新增本文件 + `README.md` 一行链接 |
| 预期结果 | 成功：改动落在 PR 分支，业务代码零改动 |
| 用途 | 证明 review 后的 follow-up 交付链路可用 |

## 这份演示证明了什么、没证明什么

- **证明了**：review 之后确实能再起一次跟进交付，改动被正确写进工作树并推到 PR 分支；「勿改业务代码」的边界在跟进场景下同样被守住（`git diff` 里只有文档）。
- **没有证明**：跟进交付能处理冲突分支、能修复真实的测试失败、或能保证 review 意见被完整理解。这次只是把一次文件搬移＋补文档走完，链路通不等于判断对。

## 生命周期：这是一次性探针

- 本文件是**一次性的交付探针**，不含任何测试或业务逻辑，删掉不会影响仓库任何功能。
- **随时可以安全删除**，不需要额外迁移或清理；删除它就是唯一的下线动作。
- 文件名 `followup-demo.md` 是这类跟进演示固定复用的名字，下一轮跟进运行会直接覆盖它（覆盖即更新，不新增文件）；表里的「运行 ID」用来标明最后一次是哪次运行改的，不要按运行 ID 拆分文件名。

## 和正常任务的区别

正常任务的产出是「能合并的测试 PR」；这次演示的产出是「review 意见被落地的证据」。两者共同的底线是：PR 里说清楚改了什么、为什么改，让人不看代码也能判断该不该合。
